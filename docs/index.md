## 提供できること

**1. 仕様が固まっていない機能を、関係者と合意しながら設計から検証まで前に進める**
設計書で判断の根拠を示してPdMやQAと合意を取り、DB設計、実装、QAテスト仕様書作成まで責任を持って進めます。直近ではLLMを用いた機能で、約3,000ペアの実データ評価により判定基準の誤適合を2.0%から0件にするなど、正解が定まらない領域での検証設計を担いました。

**2. バックエンドとクラウドインフラを一体で構築する**
GoとTypeScriptによるAPI・バッチ開発と、AWS・GCP上のインフラ設計およびTerraform・CloudFormationによるコード化、CI/CD整備をまとめて引き受けます。無停止でのデータ移行やデプロイ時間の半減など、運用を含めた構築実績があります。

**3. 金銭や個人情報を扱う領域を、事故が起きない構造で設計する**
決済、クレジットカード、銀行、マイナンバー、暗号資産の各領域で開発してきました。冪等性による二重処理防止、KMSによる秘密鍵の非保持、権限変更の監査通知など、法令や資産保全の要件をシステム構造で担保する設計を得意としています。

**4. 少人数チームの開発リード**
顧客との要件定義、工数見積、オフショアメンバー4名のマネジメントを設計・実装と並行して担い、認識ズレによる手戻りなく完遂した実績があります。

## 自己PR

SIerでの金融系システム開発、決済事業会社での開発・運用を経て、2019年からフリーランスとして13案件に参画してきました。実務経験は約11年、一貫して「仕様が固まっていない、あるいは業界固有の知識が必要な領域」を任されてきました。

強みは、未知の領域を短期間で実務水準まで引き上げ、自分で決めて前に進める力です。ドキュメントの乏しい暗号資産のプロトコルを公式実装から読み解いて署名やシリアライズを自前で実装したり、LLMの出力品質を実データで定量評価して判定基準を較正したりと、前例のない課題に対して調査・仮説・検証のサイクルを自力で回してきました。判断に迷う点は早期に相手へ持ち込み、決めるべきことを決めてから手を動かすため、手戻りが少ないと評価されています。

直近ではClaude Codeを実装・調査・テストデータ準備に組み込み、作業時間を約3分の1に短縮しました。短縮分は納期の前倒しと、設計や要件確認への時間配分に充てています。少人数チームで裁量を持ち、仕様策定から運用までを一貫して担うプロジェクトで最も力を発揮します。

#### インフルエンサーマーケティングプラットフォーム開発（2026年7月～現在）

**概要**
上場インフルエンサーマーケティング企業が2026年2月にリリースした、AIがインフルエンサーを自動選定・オファーする広告運用SaaS。リリース直後の成長初期における、AI選定の根拠提示など中核機能の開発。

**役割**
開発メンバー（エンジニア5名のチーム。機能ごとに実装リードが設計から実装、QA、リリースまで責任を持つ体制で、インフルエンサー選定理由提供機能と手動オファーページの実装リードを担当。他機能や他チームと調整しながら、設計書（PDD）作成から実装、QAテスト仕様書作成までを担当）

**担当業務**
- インフルエンサー選定理由提供機能の設計・実装（実装リード）
  - PDD作成、DBスキーマ設計、LLMを用いた選定理由生成バッチ、一覧APIの拡張、広告主向け画面と社内管理画面のUI実装、QAテスト仕様書作成
- 手動オファーページの設計・実装（実装リード）
  - オファー種別カラムの追加と既存データのbackfillジョブ、料金内訳プレビューAPI、候補検索APIのフィルタ拡張
- アドクレジット付与ラベル機能の設計・実装（クレジット管理ドメインからフロントエンドまで）
- 郵便番号による住所自動補完機能（外部API連携をフロントエンドのプロキシからバックエンドAPIへ移設、APIキーのTerraform管理）
- フィーチャーフラグによる段階的リリース（stg→prod）、Metabaseダッシュボードの更新

**成果**
- 選定理由生成では、約50件の理由候補に対し「閾値やフラグで機械判定できる適格判定」と「LLMによる意味判定」の2段構成を設計し、コードで判定できる基準はLLMのプロンプトから外した。stg実データ約3,000ペアの評価で基準の誤適合を2.0%から0件にし、閾値は本番の全インフルエンサー約1.6万件の分布を実測して較正した。実データで裏付けられない理由候補4件は候補から除外し、根拠のない理由が表示されないようにした。
- LLM呼び出しは契約単位に独立させ、失敗時はプロセス内でリトライせず次回の毎時バッチに任せる設計とし、部分保存や多重生成を防ぎつつリトライ機構の実装を不要にした。
- 手動オファーページでは、既存のオファー作成APIを流用し新設を料金プレビューAPIのみに絞る判断をPDDで確定し、実装範囲と既存画面への影響を抑えた。
- オファー送信では、送信方式ごとの失敗時の扱いをPDDで定義した。手動指名の送信は同期処理として一部の失敗を許容し、全員への配信は非同期ジョブとした上で、Datadogのモニターで失敗を検知し、失敗した相手だけを再送できるようにした。
- 稼働中のテーブルに必須のオファー種別カラムを追加する際、カラム追加、書き込み開始、既存データのbackfill、NOT NULL化の順に段階的に進め、サービスを止めずに移行した。
**使用技術**
TypeScript | Python | NestJS | Next.js | Kysely | Prisma | PostgreSQL | Redis | Bull | OpenAI API | Zod | Vitest | Storybook | Kubernetes | ArgoCD | Terraform | GitHub Actions | Datadog | Metabase | Claude Code

**概要**
オープンソース自動運転ソフトウェアを開発する自動運転スタートアップにおける、AI学習用データセットの社内基盤。研究開発フェーズのデータパイプラインとAPIの開発。

**役割**
開発メンバー（エンジニア3名のチームで、APIとワークフローの機能設計・実装を担当）

**担当業務**

- Step FunctionsとAWS Batchを用いた、以下を並列実行するパイプラインの構築
  - 学習用データセットのメタデータの抽出・登録
  - 学習用データセットの画像データから動画を生成
- S3 Object VersionIDを用いた学習用データの整合性維持
- APIエンドポイントおよびCLIツールの機能追加
- CloudFormationによるインフラ構築

**成果**

- 動画生成に利用していた共通ライブラリで、キーフレームのみで出力した動画の先頭と末尾に非キーフレームが混入する不具合を発見した。フレームの連結リストを追い、カメラごとの先頭フレームをキーフレームまで進める処理と、終端到達時の停止条件の欠落を修正し、担当外のモジュールにも自ら修正を出し、取り込まれた。

#### ブロックチェーンゲーム開発（2023年10月～2024年11月）

**概要**
大手ITグループのWeb3事業として企画されたNFTトレーディングカードゲームの新規立ち上げ。

**役割**
開発リーダー（タスクの割り振り、進捗管理、他チームとの連携、オフショアメンバー4名へのタスク割り振りとレビューを、設計・開発と並行して担当）

**担当業務**
ブロックチェーンゲームのブロックチェーンアクセス機能の構築
- 企画サイドや他のゲーム機能チームと要件をすり合わせ、担当タスクを明確化
- SQS、Lambda、ECS、DynamoDB、SNSなどを用いたインフラの構築
- DynamoDBのテーブルおよびインデックス設計
- CloudWatch Alarmによる監視機能の構築
- GitHub ActionsによるCI/CDの構築
- Lambda関数やブロックチェーンイベントのリスナーをNode.jsで実装
- NFTコントラクト、NFT制御用コントラクトの作成（Solidity）

**成果**
- パックとカードの紐付けをERC-6551（トークンにアカウントを持たせる規格）に準じてオンチェーンで実装する企画側の要求に対し、開封ごとに発生するアカウント生成と移転のガスコスト、および実装の複雑さに見合うユーザー・事業上の利点がないことを示し、カードの所有権のみオンチェーンに残して紐付けロジックはオフチェーンに寄せる設計に変更した。
- ブロックチェーンはトランザクションが送信アドレス単位で直列実行されるため処理性能に上限があったが、KMS管理の鍵をアドレス単位で払い出し、DynamoDBの条件付き書き込みによる排他制御で複数アドレスに分散して並列実行する仕組みを構築した。秘密鍵をアプリケーション側に一切保持せず、キーポリシーの変更はCloudTrail経由でEventBridgeが検知してSlackへ即時通知する構成とし、鍵の保管と権限変更の監査を含めたセキュリティ設計とした。
- NFTの二重発行や資産の二重送付を防ぐため、リクエストIDによる冪等性チェック、SQSの部分バッチ失敗レポート、デッドレターキュー、規定回数失敗時のSlack通知を組み合わせ、再実行しても安全なリカバリ設計とした。
- オフショアメンバー4名に対し、質問票やチャットで随時質問を受け付け、定例で仕様の認識を合わせる運用を徹底した。初期に発生した想定と異なる実装を最後に、以降は認識ズレによる手戻りなく開発を進めた。

**使用技術**
TypeScript | Solidity | SQS | Lambda | DynamoDB | CloudWatch | CloudTrail | EventBridge | SNS | ECS | KMS | SSM Parameter Store | ALB | RDS | Terraform | GitHub Actions
